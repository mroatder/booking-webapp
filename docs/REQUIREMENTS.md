# ระบบจองห้องประชุมและรถ - Requirements

สถานะเอกสาร: **ร่างสำหรับยืนยัน (Draft - รอ dev ยืนยัน)**

## 1. ขอบเขตระบบ (Scope)

ระบบเว็บแอปพลิเคชันสำหรับใช้งานภายในองค์กร (intranet) เพื่อ:

1. จองห้องประชุม - ดูห้องว่าง จอง/แก้ไข/ยกเลิก จองซ้ำรายสัปดาห์ เช็คอินผ่านคอมพิวเตอร์/เว็บ
2. จองรถบริษัท - พนักงานส่งคำขอใช้รถ แอดมินพิจารณาและจัดรถ+คนขับให้ (ทดแทน Google Form เดิม)
3. บริหารจัดการคนขับ (พนักงานขับรถของบริษัท และคนขับภายนอก)
4. ผู้ดูแลระบบจัดการห้อง/ผู้ใช้/คำขอรถ/คนขับ/รายงาน ผ่านหน้า Admin
5. แสดงผลสถานะห้องประชุมแบบเรียลไทม์บน tablet หน้าห้อง (ไม่ต้อง login)

ระบบต้องใช้งานได้ทั้งบนคอมพิวเตอร์และมือถือ รองรับ 2 ภาษา (ไทย/อังกฤษ) และทำงานได้ภายในเครือข่าย WiFi บริษัทแม้ไม่มีอินเทอร์เน็ต (แจ้งเตือนทางอีเมลผ่าน SMTP ภายในเท่านั้น - ~~LINE~~ ตัดออก dev 2026-09-30)

## 2. ประเภทผู้ใช้และสิทธิ์ (Roles)

ยืนยันแล้วว่าใช้ 2 role (ตัด Approver ออกเพราะไม่มีขั้นตอนอนุมัติแยกต่างหาก, ตัด Driver ออกเพราะคนขับไม่ต้อง login เข้าระบบเลย - Admin เป็นผู้จัดรถและทราบตารางคนขับเองอยู่แล้ว):

| Role | สิทธิ์ |
|---|---|
| **Employee** (พนักงานทั่วไป) | จอง/แก้ไข/ยกเลิกห้องประชุมของตัวเอง, ส่งคำขอใช้รถ, ดูสถานะคำขอของตัวเอง, สลับภาษา |
| **Supervisor** (หัวหน้างาน - เพิ่ม 2026-09-29, migration 016) | สิทธิ์เท่ากับ Employee (ขอรถ/เลือกผู้โดยสารได้ในแผนกหลักเหมือนกัน) - ขอรถไปงานนอกเองได้รับการอนุมัติอัตโนมัติ |

**ระดับผู้อนุมัติ (ไม่ใช่ role - 2026-10-05, migration 028)**: Admin กำหนดให้ผู้ใช้คนใดก็ได้เป็น **ผู้อนุมัติระดับ 1 / 2 / 3** (คนละเรื่องกับ role) - ผู้อนุมัติเห็นแท็บ "รออนุมัติ" ในเมนูจองรถ, อนุมัติ/ไม่อนุมัติ (ต้องใส่เหตุผล) คำขอรถไปงานนอกที่ผู้ขอเลือกตัวเอง และอัปโหลดรูปลายเซ็น/ตราประทับครั้งเดียวในหน้าโปรไฟล์ |
| **Admin** | ทำทุกอย่างที่ Employee ทำได้ + จัดการห้องประชุม (CRUD), จัดการคำขอรถ (พิจารณา/จัดรถ+คนขับ), จัดการคนขับ (ภายใน/ภายนอก), จัดการผู้ใช้ (local account + กำหนด role), จัดการ tablet token ต่อห้อง, ดูรายงาน/export Excel, ดู audit log |

**รายชื่อไม่ login (2026-10-09, migration 036)**: พนักงานที่ไม่มีคอมพิวเตอร์ Admin สร้างรายชื่อไว้เองโดยติ๊กออก "สร้างบัญชีที่ login ได้" - ไม่มี username/รหัสผ่าน (ระบบสร้าง Username ภายใน `nologin-xxxx` เอง, ไม่แสดงใน UI/API), `AuthSource = 'None'`, บังคับ role Employee และไม่มีระดับผู้อนุมัติ, login ไม่ได้ (ไม่ลอง LDAP), ขอรถเองไม่ได้ - ถูกเลือกเป็นผู้โดยสารโดยหัวหน้า/Admin ได้เหมือนพนักงานทั่วไป; ไม่มีอีเมลก็ไม่ถูกส่งแจ้งเตือน (ข้ามเงียบ)

หมายเหตุ: **คนขับ (ทั้งภายในและภายนอก) ไม่มี account/login ในระบบเลย** - เป็นแค่ข้อมูล (ชื่อ+เบอร์โทร) ที่ Admin จัดการและเลือกใช้ตอนจัดรถ โดย Admin เป็นผู้ทราบว่าใครว่าง/ไม่ว่าง หรือกำลังขับไปที่ไหนอยู่จากงานที่ระบบบันทึกไว้ ไม่ต้องให้คนขับเข้ามารายงานสถานะเอง

Login รองรับ 2 ทาง: Active Directory (LDAP, plain - ไม่เข้ารหัส, port 389 - รายละเอียด domain/OU/กลุ่ม admin จะกำหนดผ่าน environment config ตอน deploy จริงโดยประสานกับ IT) และ Local account (สำหรับผู้ใช้ที่ไม่มี user ใน AD)

## 3. User Stories

### ห้องประชุม
- ในฐานะพนักงาน ฉันต้องการดูว่าห้องไหนว่างในช่วงเวลาที่ต้องการ เพื่อเลือกห้องจองได้ทันที
- ในฐานะพนักงาน ฉันต้องการจองห้องได้ทันทีโดยไม่ต้องรออนุมัติ ตราบใดที่ห้องว่างจริง
- ในฐานะพนักงาน ฉันต้องการตั้งจองซ้ำรายสัปดาห์ (เช่น ประชุมทีมทุกวันจันทร์) โดยไม่ต้องจองทีละครั้ง
- ในฐานะพนักงาน ฉันต้องการยกเลิกการจองของตัวเองได้ และไม่สามารถลบ/แก้ไขการจองของคนอื่นได้
- ในฐานะพนักงานที่เข้าประชุม ฉันต้องการกดเช็คอินผ่านคอมพิวเตอร์/เว็บ (จากหน้าการจองของฉัน) เพื่อยืนยันว่าใช้ห้องจริง
- ในฐานะระบบ ฉันต้องปล่อยห้องอัตโนมัติถ้าไม่มีใครเช็คอินภายใน 10 นาทีหลังเวลาเริ่ม เพื่อให้คนอื่นจองซ้อนได้
- ในฐานะพนักงานที่ใช้ห้องเกินเวลา และมีคนจองต่อ ฉันต้องการให้ระบบแจ้งเตือนทั้งสองฝ่าย (ไม่ตัดสิทธิ์อัตโนมัติ)
- ในฐานะ Admin ฉันต้องการเพิ่ม/แก้ไข/ลบห้องประชุมได้เองผ่านหน้าจัดการ โดยไม่ต้อง deploy ใหม่

### รถ
- ในฐานะพนักงาน ฉันต้องการส่งคำขอใช้รถผ่านระบบ (แทนการกรอก Google Form) พร้อมระบุวันเวลา จุดรับ-ส่ง ปลายทาง จำนวนผู้โดยสาร และประเภทรถ
- ในฐานะ Admin ฉันต้องการเห็นคำขอรถทั้งหมด พิจารณา และจัดรถ+คนขับ (ภายในหรือภายนอก) ให้คำขอนั้น
- ในฐานะ Admin ฉันต้องการเห็นสถานะว่าง/ไม่ว่างของคนขับภายในแบบปฏิทิน (คำนวณจากงานที่มอบหมายไปแล้วในระบบ) เพื่อเลือกคนขับที่ว่างจริงในช่วงเวลานั้น โดยไม่ต้องให้คนขับเข้าระบบมารายงานสถานะเอง
- ในฐานะพนักงาน ฉันไม่สามารถเบิกรถไปขับเองได้ - ทุกการจองรถต้องมีคนขับเสมอ

### ทั่วไป
- ในฐานะผู้ใช้ ฉันต้องการสลับภาษาไทย/อังกฤษได้จากทุกหน้า และระบบจำภาษาที่เลือกไว้ในครั้งถัดไป
- ในฐานะผู้ใช้ ฉันต้องการใช้งานระบบบนมือถือได้สะดวกเทียบเท่าคอมพิวเตอร์
- ในฐานะ Admin ฉันต้องการดูรายงานสรุปการใช้ห้อง/รถ และ export เป็น Excel ได้
- ในฐานะ Admin ฉันต้องการตรวจสอบย้อนหลังได้ว่าใครจอง/แก้ไข/ยกเลิกอะไรเมื่อไหร่ (audit log)
- ในฐานะทีม IT ฉันต้องการ endpoint สำหรับ monitoring (health check) เพื่อเฝ้าระวังระบบผ่าน Zabbix

## 4. กฎทางธุรกิจ (Business Rules)

### ห้องประชุม
1. **ไม่ต้องมีการอนุมัติ** - จองได้ทันทีถ้าห้องว่าง
2. **ห้ามจองซ้อน (double booking)** - ต้องป้องกัน race condition ด้วย transaction + lock ระดับฐานข้อมูล (UPDLOCK, HOLDLOCK) ห้ามพึ่ง lock ระดับ application เพียงอย่างเดียว
3. จองล่วงหน้าได้สูงสุด **90 วัน**
4. รองรับการจองซ้ำรายสัปดาห์ (recurring weekly) - ยกเลิกได้ทั้งชุดหรือยกเลิกเฉพาะครั้งใดครั้งหนึ่ง
5. ผู้จองแก้ไข/ยกเลิกได้เฉพาะการจองของตัวเอง (Admin แก้ไข/ยกเลิกของใครก็ได้)
6. **เช็คอิน**: ต้องเช็คอินภายใน **10 นาที** หลังเวลาเริ่มประชุม โดย**เช็คอินผ่านคอมพิวเตอร์/เว็บ** (ปุ่มเช็คอินอยู่ที่หน้ารายการ/รายละเอียดการจองของผู้จอง ไม่ใช่บน tablet) - ถ้าไม่เช็คอินภายในเวลา ระบบปล่อยห้องอัตโนมัติ (สถานะกลับเป็นว่าง ให้คนอื่นจองทับช่วงเวลานั้นได้)
7. **ใช้เกินเวลาที่จอง**: ถ้ามีคนจองต่อในช่วงเวลาถัดไป ระบบแจ้งเตือนทั้งเจ้าของห้องปัจจุบันและผู้จองถัดไป โดย**ไม่ตัดสิทธิ์หรือบังคับออกจากห้องอัตโนมัติ** - **ปรับ 2026-10-05 (dev เลือก)**: ระบบไม่มีทางรู้ว่ายังมีคนอยู่ในห้องหลังเวลาจบ จึงเปลี่ยนเป็น**ส่งอีเมลเตือนผู้จองก่อนหมดเวลา 5 นาที** เมื่อมีคนจองห้องเดียวกันต่อภายใน 15 นาทีหลังเวลาจบ (เตือนครั้งเดียวต่อการจอง)
8. Tablet หน้าห้องมีไว้เพื่อ**แสดงผลสถานะห้องและตารางการใช้ห้อง** - ~~ไม่มีปุ่มเช็คอิน~~ **ปรับ 2026-10-05 (dev ยืนยัน): เช็คอินที่จอหน้าห้องได้ด้วย** (การจองของห้องที่จอผูกอยู่ สถานะ Booked เท่านั้น ไม่ต้อง login - ข้อสังเกต: ใครอยู่หน้าห้องก็กดได้) เข้าถึงด้วย **token เฉพาะห้อง** (ไม่ต้อง login) - Admin เป็นผู้สร้าง/จัดการ token ต่อห้องได้ (revoke/regenerate ได้) - **ปรับ 2026-09-29**: token เป็นของ**อุปกรณ์ (จอ)** ไม่ใช่ห้อง - Admin เพิ่ม/แก้/ลบอุปกรณ์ ผูกหรือย้ายห้องได้ (1 ห้องมีได้หลายจอ, จอยังไม่ผูกห้องได้ จะขึ้นข้อความรอผูกห้อง), คัดลอกลิงก์ไปเปิดบน tablet, ออกลิงก์ใหม่ (ลิงก์เดิมใช้ไม่ได้), ลบอุปกรณ์ได้เสมอ (ไม่มีประวัติที่อื่นอ้างถึง)

### รถ
1. พนักงานส่งคำขอผ่านระบบ → **Admin เป็นผู้พิจารณาและจัดรถ+คนขับให้** (ไม่มีสถานะ "อนุมัติ/ไม่อนุมัติ" แบบทางการ - Admin จัดสรรทรัพยากรให้โดยตรง)
2. ทุกการจองรถต้องมีคนขับเสมอ - **ไม่มีกรณีขับเอง**
3. คนขับ**และรถ**ที่ลงทะเบียน (รถบริษัท + รถเช่า): ระบบคำนวณสถานะว่าง/ไม่ว่างแบบ**ช่วงเวลา (time slot / calendar)** จากงานที่ Admin มอบหมายไว้แล้วในระบบ (ไม่ใช่ให้คนขับกรอกเอง) ใช้ป้องกันไม่ให้ Admin จัดคนขับคนเดียวกันซ้อนช่วงเวลาโดยไม่ได้ตั้งใจ - **คนขับไม่ต้อง login และไม่ต้องรายงานสถานะใดๆ เข้าระบบเอง**
4. ~~คนขับภายนอก: เก็บแค่ชื่อ+เบอร์โทร~~ → แทนด้วยกฎข้อ 9 (รถ 3 แบบ)
5. คำขอรถ 1 ครั้ง**ข้ามหลายวันได้** (เช่น ออกวันจันทร์ กลับวันพุธ) - คนขับภายในจะไม่ว่างตลอดช่วงนั้น (dev ยืนยัน 2026-09-28)
6. ส่งคำขอรถล่วงหน้าได้สูงสุด **90 วัน** และห้ามขอย้อนหลัง (กฎเดียวกับห้องประชุม - dev ยืนยัน 2026-09-28)
7. พนักงานแก้ไข/ยกเลิกคำขอของตัวเองได้**เฉพาะตอนยังรอดำเนินการ (Pending)** - หลัง Admin จัดคนขับแล้ว ต้องให้ Admin เป็นผู้ยกเลิก/แก้ไข เพราะคนขับภายนอกนัดกันนอกระบบ ถ้าพนักงานยกเลิกเอง Admin/คนขับจะไม่รู้ (dev ยืนยัน 2026-09-28)
8. **ทุกช่องในฟอร์มขอรถต้องกรอก รวมถึงลิงก์แผนที่** (dev ยืนยัน 2026-09-28 หลังจบ M6 - เดิมลิงก์แผนที่เป็นช่องไม่บังคับ) - **ปรับ 2026-09-29**: แยกลิงก์แผนที่จุดรับกับปลายทาง ถ้าจุดไหนเป็น "ที่บริษัท" ติ๊กแทนได้ไม่ต้องแนบแผนที่; คำขอรถโอทีไม่มีช่องสถานที่/แผนที่ (ใช้สายรถของพนักงานแต่ละคน)
9. **รถมี 3 แบบ** (dev ยืนยัน 2026-09-28):
   - **รถบริษัท** (คนขับรถผู้บริหาร เอามาวิ่งงานทั่วไปด้วย): ลงทะเบียนคนขับ + รถ (ทะเบียน/ประเภท/จำนวนที่นั่ง/รายละเอียด) ตอนจัดรถเลือกคนขับ 1 คน + รถ 1 คัน
   - **รถเช่า** (รถรับส่งพนักงานจากบริษัทรถเช่า ใช้เมื่อต้องการที่นั่งเยอะ): ลงทะเบียนบริษัทรถเช่า (+เบอร์ติดต่อ) พร้อมคนขับและรถของบริษัทนั้น แยกกัน ตอนจัดรถเลือกบริษัท → คนขับ + รถของบริษัทนั้น
   - **เรียกรถออนไลน์** (Grab - ใช้เมื่อรถบริษัทไม่ว่างหรือไปไกล คนขับเปลี่ยนทุกเที่ยว): ลงทะเบียนแค่ชื่อบริการ ตอนจัดรถกรอก **ชื่อคนขับ + เบอร์ + ทะเบียน** ของเที่ยวนั้น (บังคับทั้ง 3 ช่อง)
10. **กันจัดซ้อนเวลา** ทั้งคนขับและรถของรถบริษัท/รถเช่า (ไม่เช็คเรียกรถออนไลน์) - ประเภทรถมีแค่ รถตู้/รถเก๋ง แต่รถแต่ละคันเก็บจำนวนที่นั่ง ตอนจัดรถเตือนถ้าที่นั่งน้อยกว่าผู้โดยสาร (เตือนเฉยๆ ไม่บังคับ) - ผู้จองเห็นชื่อคนขับ เบอร์ ทะเบียน ประเภท/ที่นั่ง/รายละเอียดรถ และผู้จัดรถ
11. ~~ต้องแนบไฟล์แบบฟอร์มขอใช้รถทุกคำขอรถไปงานนอก~~ → **ไม่มีการแนบไฟล์แล้ว** (HR ตกลง 2026-10-05: ใช้การอนุมัติของหัวหน้าในระบบ + ระบบออกแบบฟอร์ม W-HR-009 เป็น PDF แทน - dev: "อนุมัติแล้ว ผู้ขอไม่จำเป็นต้องแนบไฟล์") ฟอร์มขอรถไม่มีช่องแนบไฟล์ - ไฟล์ที่แนบไว้ในคำขอเก่ายังเปิดดูได้ (เฉพาะผู้ขอและ Admin); ประเภทคำขอเปลี่ยนไม่ได้หลังสร้าง
12. **พนักงานทุกคนขอรถเองได้ (รวมรถโอที)** และเลือก "พนักงานที่เดินทาง" ได้เฉพาะคนใน**แผนกหลัก**ของตัวเอง (แผนกบนสุด + แผนกย่อยทั้งหมด - ไม่จำกัดแค่แผนกย่อย เผื่อหัวหน้างานลา) ทั้ง Employee และหัวหน้างาน, Admin เลือกได้ทุกคน (dev ยืนยัน 2026-09-29)
13. **รถไปงานนอกเลือกรูปแบบการเดินทางได้: ไป-กลับ / ไปอย่างเดียว / กลับอย่างเดียว** - ไปหรือกลับอย่างเดียวกรอกแค่เวลารับ ระบบกันคนขับและรถไว้ 2 ชั่วโมงนับจากเวลารับ (dev ยืนยัน 2026-09-29)
14. **รถโอที (รถรับส่งพนักงานนอกเวลา)** - เลือกประเภทเที่ยว: รับมาบริษัท (เช้า) / ส่งกลับบ้าน (เย็น) / ไป-กลับ (วันหยุด) + วันเวลา + รายชื่อพนักงาน (ไม่มีแขก) - พนักงานแต่ละคนมี**สายรถ + จุดขึ้นรถประจำ** (Admin ตั้งที่เมนูจองรถ > ผู้โดยสารรถรับส่ง) สายรถมีรถ+คนขับประจำ ระบบใช้แนะนำรถตอนจัด; ใส่พนักงานที่ยังไม่มีสายประจำได้ แต่ระบบขึ้น ⚠️ ให้ Admin เห็น (dev 2026-09-29)
15. **คำขอโอทีเที่ยวเดียวกันใช้รถคันเดียวกันได้** - "เที่ยวเดียวกัน" = เวลาออก เวลากลับ และประเภทเที่ยวตรงกันทุกอย่าง (ต่างกันแม้ไม่กี่นาทีถือเป็นคนละเที่ยว) ไม่นับเป็นการจัดซ้อนเวลา - Admin ดูรวมตามสาย (รายการเที่ยวรายวัน + ใบรายชื่อ) และ**จัดรถทั้งเที่ยว**ได้ในครั้งเดียว ตอนจัดเตือนที่นั่งจากจำนวนผู้โดยสารรวมทุกคำขอ (dev 2026-09-29)
16. **พนักงาน 1 คนมีชื่อได้แค่ 1 คำขอในช่วงเวลาเดียวกัน** - ถ้ามีชื่ออยู่ในคำขออื่นที่ยังไม่ยกเลิกและเวลาทับกัน ระบบไม่ให้บันทึก แจ้งชื่อคนและเลขคำขอที่ชน (ใช้ทั้งรถนอกและรถโอที - กันต่างคนต่างขอให้คนเดียวกันจนชื่อซ้ำ/นับที่นั่งเกิน) (dev 2026-09-29)
17. **ลบคนขับ / รถ / ผู้ให้บริการได้จริงเฉพาะรายการที่ไม่มีอะไรผูกอยู่** - ถ้าเคยถูกจัดให้คำขอรถ (ทุกสถานะ รวมที่ยกเลิก), เป็นคนขับประจำรถ, อยู่ในสายรถ หรือ (ผู้ให้บริการ) ยังมีคนขับ/รถ/สายลงทะเบียน → ลบไม่ได้ ระบบบอกเหตุผล ให้ใช้ "ปิดใช้งาน" (soft delete) แทน เพื่อไม่ให้ประวัติ "ใครขับ คันไหน" หาย (dev 2026-09-29)
18. **รถไปงานนอกต้องผ่านการอนุมัติของหัวหน้าก่อนจัดรถ** (dev+HR 2026-10-05) - ผู้ขอกรอก **เหตุผลการขอใช้รถ** (บังคับ) และ**เลือกผู้อนุมัติ 1 คน** จากผู้มีระดับอนุมัติ (1/2/3) ในแผนกหลักของตัวเอง (เรียงระดับ 1 → 3 - ระดับ 1 ไม่อยู่ก็เลือกระดับที่สูงกว่าได้, อนุมัติคนเดียวพอ ไม่ต้องไล่ทุกระดับ); ผู้ขอที่เป็นหัวหน้างานหรือมีระดับอนุมัติเอง → **อนุมัติอัตโนมัติ**; รถโอทีไม่ต้องอนุมัติ - สถานะการอนุมัติ: ไม่ต้องอนุมัติ / รออนุมัติ / อนุมัติแล้ว / ไม่อนุมัติ (มีเหตุผล), **Admin จัดรถได้เฉพาะคำขอที่อนุมัติแล้ว** (`APPROVAL_REQUIRED`), ผู้ขอแก้ไขคำขอ → กลับไปรออนุมัติใหม่ (Admin แก้ไม่กระทบผลอนุมัติ) - ขั้นตอน: ผู้ขอส่ง → หัวหน้าอนุมัติ → Admin ส่งแบบฟอร์ม W-HR-009 ให้บริษัทรถ (ยังไม่รู้คนขับ) → บริษัทรถแจ้งคนขับ/รถกลับมา → Admin จัดรถ → แจ้งผู้ขอ - แจ้งเตือน: ส่งคำขอ → ผู้ขอ (รับเรื่องแล้ว) + ผู้อนุมัติ, อนุมัติ → **Admin ทุกคนเท่านั้น** (ไม่แจ้งผู้ขอ - ผู้ขอได้อีเมลยืนยันเมื่อจัดรถ+คนขับแล้วเท่านั้น, dev 2026-10-05), ไม่อนุมัติ → ผู้ขอ
19. **Admin ส่งออกแบบฟอร์มการขอใช้รถ (W-HR-009 Annex B R0) เป็น PDF** ส่งให้บริษัทรถ - รถนอกที่ยังไม่ยกเลิกและไม่ติดการอนุมัติ (อนุมัติแล้ว หรือคำขอเก่าก่อนมีระบบอนุมัติ - แบบหลังช่อง Approved by ว่างไว้เซ็นมือ): ว/ด/ป, ผู้ขอ, แผนก, พนักงานขับรถ, วันที่ขอใช้, สถานที่, เหตุผล, เวลาออก/เข้า, Requested by, Approved by = **รูปลายเซ็น/ตราที่ผู้อนุมัติอัปโหลดไว้** (PNG/JPG ≤ 1 MB - ตรา DocuWorks ใช้ตรงไม่ได้ ต้องบันทึกเป็นรูปก่อน; ไม่มีรูปแสดงเป็นชื่อ) + ชื่อ + เวลาอนุมัติในระบบ
20. **เดินทางกลุ่ม (กิจกรรม/รถตู้)** (2026-10-07) - Admin สร้าง/แก้ไข/ลบกิจกรรม (ปลายทาง วันเดินทาง วันปิดรับลงชื่อ); พนักงานทุกคนลงชื่อให้ตัวเองหรือลงชื่อแทนผู้อื่นได้ (เบอร์โทร จุดขึ้นรถ จำเป็น) - **ผู้เดินทางต้องเป็นพนักงานในระบบ เลือกจากรายชื่อเท่านั้น ห้ามพิมพ์ชื่อเอง** (dev 2026-10-07): ลงแทนคนอื่นเลือกได้เฉพาะในแผนกหลักของตัวเอง (Admin เลือกได้ทุกคน) และ **ชื่อ รหัสพนักงาน แผนก ระบบเติมจากข้อมูลผู้ใช้จริง** จนกว่าจะเลยกำหนดปิดรับ - **ไม่จำกัดจำนวนผู้ลงชื่อ ไม่มีเรื่องที่นั่ง** (ไม่ใช่ที่นั่งรถ Admin จัดรถเองว่าใช้สายไหน/รถอะไร ตาม Phase 2); ยกเลิกได้เฉพาะ Admin / ผู้ลงชื่อให้ / เจ้าของรายชื่อ - **การส่งออก CSV/Excel รายชื่อผู้เดินทางเป็นสิทธิ์ของ Admin เท่านั้น** (ผู้ใช้อื่นไม่เห็นปุ่ม)
   - **รายละเอียดการขึ้นรถ (Admin กรอก → ประกาศ → พนักงานเห็น)** (dev 2026-10-07): หลังส่งรายงานให้บริษัทรถและบริษัทรถแจ้งกลับ Admin กรอกที่ จัดการคำขอรถ > เดินทางกลุ่ม > "รายละเอียดการขึ้นรถ": **สายรถ** (ประเภทรถ ตู้/เก๋ง, ชื่อสาย, ทะเบียนรถ, ชื่อ/เบอร์คนขับ - พิมพ์เองหรือเลือกจากรถ/คนขับที่มีในระบบเพื่อเติมให้ก็ได้ แต่เก็บเป็นข้อความ ไม่ผูก FK) แล้ว **เลือกแค่ชื่อ** ผู้เดินทางที่ขึ้นแต่ละสาย (จุดขึ้นรถใช้ตามที่ลงชื่อไว้ เลือกได้หลายคนพร้อมกัน) พร้อม **เวลาขึ้นรถตามจริง** (พิมพ์ เช่น 05:30, ตั้งทั้งสายได้, วันเดินทาง) → กด **ดูรายงาน** ตรวจสอบความถูกต้อง (ดาวน์โหลด Excel ได้) → กด **ประกาศ** → พนักงานเห็นที่แท็บ **"การขึ้นรถของฉัน"** ในหน้า **การเดินทางกลุ่ม** (หน้านี้มี 2 แท็บ: ลงชื่อขึ้นรถ | การขึ้นรถของฉัน; ลิงก์ในอีเมลเปิดแท็บหลังด้วย `?tab=boarding`) - เป็น **รายการ (ตาราง) 1 สาย = 1 แถว** (กิจกรรม วันเดินทาง สาย/ประเภทรถ/ทะเบียน ผู้เดินทางของฉัน เวลาขึ้นรถ; ตัวสลับ กำลังจะถึง | ที่ผ่านมาแล้ว หน้าละ 7) กด "ดูรายละเอียด" เปิด modal แสดง **ทั้งสายรถ**: ข้อมูลรถ/คนขับ + ตารางผู้เดินทางทุกคนในสาย (ลำดับ เวลา ชื่อ แผนก **เบอร์โทร** จุดขึ้นรถ - **แสดงเบอร์โทรของเพื่อนร่วมสายเพื่อให้โทรหากันได้ (dev 2026-10-21) แต่ไม่แสดงรหัสพนักงาน** และมีปุ่ม **ส่งออก Excel ต่อสาย** (ทั้งในแถวและใน modal; ไฟล์มีข้อมูลเท่ากับที่เห็นในหน้า, เซิร์ฟเวอร์ตรวจว่าเป็นสายของตัวเอง)) ไฮไลต์แถวของตัวเอง/คนที่ลงชื่อให้ และได้ **อีเมล (ไทย) พร้อมไฟล์ Excel สรุป** ระบุสาย/เวลา/จุดขึ้น/ทะเบียน/คนขับ; **ผู้ที่เห็น/ได้รับ = เจ้าของรายชื่อ + คนที่ลงชื่อให้ + Admin เท่านั้น** (เห็นสายที่ตัวเองอยู่ทั้งสาย; อีเมลและไฟล์ Excel แนบมีเฉพาะแถวของตัวเองและคนที่ตัวเองลงชื่อให้; คนที่ไม่มีอีเมลข้ามอีเมล แต่เห็นในเว็บ); ก่อนประกาศพนักงานไม่เห็น, แก้หลังประกาศ = พนักงานเห็นข้อมูลล่าสุดในเว็บทันที (อีเมลที่ส่งแล้วไม่เปลี่ยน, "ประกาศอีกครั้ง" = ส่งอีเมลใหม่ทุกคน), ยกเลิกประกาศได้ (ไม่มีอีเมล); รายงานที่ส่งบริษัทรถจะมีคอลัมน์สาย/เวลา/ทะเบียน/คนขับเพิ่มเมื่อจัดสายแล้ว
   - **รายงานรายชื่อ + จุดขึ้นรถ (Excel) - Admin เท่านั้น** (HR ตกลง 2026-10-07: บริษัทรถจัดรถเอง เราแค่ส่งตำแหน่งขึ้นรถให้): ปุ่ม "ส่งออกรายงาน (Excel)" ที่เมนูจองรถ > จัดการคำขอรถ > ตัวสลับ "เดินทางกลุ่ม" (และในหน้ารายชื่อของกิจกรรม) → ไฟล์ .xlsx มีหัวกิจกรรม (ปลายทาง วันไป-กลับ จำนวนผู้เดินทาง ขาไป/ขากลับ) + ตาราง ลำดับ/ชื่อ/รหัสพนักงาน/แผนก/เบอร์/จุดขึ้นรถ/**ลิงก์แผนที่ (คลิกได้)**/เที่ยว/หมายเหตุ เรียงตามจุดขึ้นรถ - Admin ดาวน์โหลดแล้วส่งให้บริษัทรถเอง (ระบบไม่ส่งอีเมลให้); **ไม่มีการจัดสาย/จัดรถ/คำนวณเส้นทาง/พิกัด** (เคยทำ Smart Route แล้วถอนออก) - ลิงก์แผนที่ใช้ได้ทุกรูปแบบ (ยาวได้ถึง 2000 ตัวอักษร) ระบบไม่ตรวจว่าอ่านพิกัดได้

### ห้องประชุม (เพิ่มเติม)
9. **ลบห้องได้จริงเฉพาะห้องที่ไม่เคยมีการจองเลย** - มีประวัติแล้วให้ **ปิดใช้งาน** แทน (ห้องที่ปิด: จองใหม่ไม่ได้, ไม่แสดงในรายการห้อง/ปฏิทิน/หน้าอุปกรณ์, จอ tablet ของห้องหยุดทำงาน, ประวัติการจองยังอยู่ เปิดกลับได้) - ปิดใช้งานไม่ได้ถ้ายังมีการจองที่ยังไม่ถึงเวลา ต้องยกเลิกก่อนเพื่อให้ผู้จองรู้ (dev 2026-09-29) - จอ tablet ของห้องที่ปิดใช้งานจะขึ้นข้อความรอผูกห้อง

### ผู้ใช้
2. **Admin เพิ่มผู้ใช้จาก AD ได้โดยตรง** โดยไม่ต้องรอให้ผู้ใช้ login ครั้งแรก - ค้นหาด้วยชื่อ/username/อีเมล แล้วเลือกหลายคนพร้อมกำหนดสิทธิ์ (Employee/Admin) ได้เลย แสดงเฉพาะบัญชี AD ที่ยังเปิดใช้งาน, คนที่มีในระบบแล้วจะข้าม (ไม่เปลี่ยนสิทธิ์เดิม) - ต้องมีบัญชีบริการ AD แบบอ่านอย่างเดียว (`LDAP_BIND_USER`/`LDAP_BIND_PASSWORD`) (dev ยืนยัน 2026-09-28)
1. **เบอร์โทรไม่ได้มาจาก AD** (AD ของบริษัทไม่มีเบอร์) - ผู้ใช้กรอก/แก้เบอร์ตัวเองได้ที่หน้า "โปรไฟล์ของฉัน" และ Admin แก้ให้ได้ในหน้าจัดการผู้ใช้ - การ login ด้วย AD จะไม่เขียนทับเบอร์ (ชื่อ/แผนก/อีเมลยัง sync จาก AD ทุกครั้งเหมือนเดิม) (dev ยืนยัน 2026-09-28)

### ระบบ / ความปลอดภัยข้อมูล
1. ทุก query กับฐานข้อมูลต้องเป็น parameterized query เท่านั้น (ห้าม string concat)
2. ข้อความในหน้าจอและ error ทั้งหมดต้องมาจากไฟล์ภาษา - backend ส่ง error code, frontend เป็นผู้แปล
3. ต้องเก็บ **audit log** ของ action สำคัญ: สร้าง/แก้ไข/ยกเลิกการจองห้อง, เช็คอิน, สร้างคำขอรถ, การจัดรถ/คนขับ, การจัดการผู้ใช้/ห้อง - พร้อมระบุ user, timestamp, action, ก่อน/หลัง (ถ้าเป็นการแก้ไข)
4. **แจ้งเตือนทางอีเมลอย่างเดียว** (~~LINE~~ ตัดออก - dev 2026-09-30) และเป็น best-effort - ถ้า SMTP ล่มหรือส่งไม่สำเร็จ ต้อง**ไม่กระทบ**การทำงานหลักของระบบ (การจอง/การจัดรถต้องสำเร็จอยู่ดี)

## 5. ข้อมูลที่ต้องเก็บ (Data)

### ผู้ใช้ (Users)
- ชื่อ-สกุล, แผนก (อ้างอิงตารางแผนก), เบอร์โทร, อีเมล, รหัสพนักงาน, role (Employee/Supervisor/Admin), **ระดับผู้อนุมัติ (1/2/3 หรือว่าง)**, **ไฟล์ลายเซ็น/ตรา** (ผู้อนุมัติ), ที่มา (AD, Local หรือ **None = รายชื่อเฉยๆ ไม่ login** - migration 036), username, password hash (เฉพาะ local account), สถานะใช้งาน

### แผนก (Departments)
- ชื่อแผนก, แผนกแม่ (เป็นโครงสร้างต้นไม้ - "แผนกหลัก" = แผนกบนสุด ใช้กำหนดขอบเขตเลือกผู้โดยสาร)

### ห้องประชุม (Rooms)
- ชื่อห้อง, ชั้น/อาคาร, สถานะใช้งาน (ปิดใช้งานได้) (~~tablet token~~ ย้ายไปที่อุปกรณ์แล้ว, ~~ความจุ (จำนวนคน)~~ - ตัดออกหลัง M2 ตามที่ dev ยืนยัน)

### อุปกรณ์ (Devices - จอ tablet หน้าห้อง)
- ชื่ออุปกรณ์, ห้องที่ผูก (ไม่ผูกก็ได้), token สำหรับลิงก์ของจอ, เวลาที่จอติดต่อมาล่าสุด (ใช้แสดงสถานะออนไลน์)

### การจองห้อง (Room Bookings)
- ห้อง, ผู้จอง, หัวข้อประชุม, วันที่, เวลาเริ่ม-สิ้นสุด, รูปแบบซ้ำ (ครั้งเดียว/รายสัปดาห์ + วันสิ้นสุดชุด), สถานะ (จองอยู่/เช็คอินแล้ว/ปล่อยอัตโนมัติ/ยกเลิก), เวลาที่เช็คอิน

### คำขอใช้รถ (Vehicle Requests)
- **เลขที่เอกสาร VR-ปี ค.ศ.-ลำดับ** (เช่น VR-2026-0001 - รันใหม่ทุกปีตามเวลาไทย, เรียงต่อกันไม่มีช่องว่าง, คำขอที่ยกเลิกยังคงเลขเดิม) - ใช้แสดง/อ้างอิงกับผู้ใช้; เลขภายใน (id) ใช้ในระบบเท่านั้น (dev 2026-09-30)
- ผู้ขอ (ชื่อ-สกุล/แผนกดึงจากโปรไฟล์), เบอร์โทรติดต่อ, **ประเภทคำขอ (รถไปงานนอก / รถโอที)**, **รูปแบบการเดินทาง (ไป-กลับ / ไปอย่างเดียว / กลับอย่างเดียว - รถนอก)**, เวลาออก, เวลากลับ, จุดรับ + ลิงก์แผนที่จุดรับ, ปลายทาง + ลิงก์แผนที่ปลายทาง (ติ๊ก "ที่บริษัท" แทนแผนที่ได้), ประเภทรถ (รถตู้/รถเก๋ง), **รายชื่อพนักงานที่เดินทาง** + จำนวนแขก (รถโอทีไม่มีแขก), ไฟล์แนบ (เฉพาะคำขอเก่า), **เหตุผลการขอใช้รถ + ผู้อนุมัติ + สถานะการอนุมัติ/เวลา/เหตุผลที่ไม่อนุมัติ (รถนอก)**, สถานะ (รอดำเนินการ/จัดรถแล้ว/ยกเลิก), รถ+คนขับที่ถูกจัดให้ + ผู้จัด/เวลาจัด
- รถโอที: ประเภทเที่ยว (เช้า/เย็น/วันหยุด) ตอนนี้อนุมานจากจุดรับ/ปลายทาง ยังไม่มีช่องเก็บของตัวเอง

### คนขับ / รถ / ผู้ให้บริการ (Drivers / Vehicles / Providers) - คนขับไม่มี login/account
- ผู้ให้บริการ: ชื่อ, ประเภท (บริษัทรถเช่า / เรียกรถออนไลน์), เบอร์ติดต่อ (เฉพาะรถเช่า), สถานะใช้งาน
- คนขับ: ชื่อ, เบอร์โทร, เจ้าของ (บริษัทเรา หรือบริษัทรถเช่า), สถานะใช้งาน - สถานะว่าง/ไม่ว่างคำนวณจากงานที่มอบหมายในคำขอรถ
- รถ: ทะเบียน, ประเภท, จำนวนที่นั่ง, รายละเอียด, เจ้าของ, สายรถประจำ, คนขับประจำ, สถานะใช้งาน
- เรียกรถออนไลน์: ไม่ลงทะเบียนคนขับ/รถ - กรอกชื่อ/เบอร์คนขับ + ทะเบียนรายเที่ยวตอนจัดรถ

### สายรถรับส่ง / ผู้โดยสารรถรับส่ง (Shuttle Routes / Passengers)
- สายรถ: บริษัทรถเช่าเจ้าของสาย, ชื่อสาย, ต้นทาง, ปลายทาง, จุดจอดตามลำดับ, เวลาวิ่งเช้า/เย็น, รถ+คนขับประจำสาย, สถานะใช้งาน
- ผู้โดยสาร: พนักงาน 1 คนมี 1 สายประจำ + จุดขึ้นรถ

### Audit Log (ตาราง `AuditLogs` - migration 035, M9 เสร็จ 2026-10-08)
- user (หรือผู้กระทำที่ไม่ใช่ผู้ใช้: `system` / `tablet` / username ที่พยายามล็อกอิน), action (รหัสแบบ `entity.verb` เช่น `vehicleRequest.approve`), entity + id, timestamp (UTC), method/path (แทน id เป็น `:id`, ไม่เก็บ token), status code, IP, รายละเอียด JSON (`before` = ค่าก่อนแก้ของ entity ที่รองรับ, `body` = ข้อมูลที่ส่งมา, `query`, `files`) - **ตัดรหัสผ่าน/โทเค็น/ลายเซ็น/hash ออกก่อนบันทึก** และจำกัดขนาด
- บันทึกอัตโนมัติ (middleware) ทุกคำขอที่แก้ข้อมูลและสำเร็จ + ล็อกอินสำเร็จ/ล้มเหลว + ระบบปล่อยห้องอัตโนมัติ; **เป็น best-effort** - เขียน log ไม่ได้ต้องไม่ทำให้การทำงานหลักล้มเหลว; ไม่มี FK ที่ UserID (log ต้องอยู่ครบแม้ผู้ใช้ถูกลบ)
- รวม action ที่ PLAN เตือนไว้: อนุมัติ/ไม่อนุมัติรถนอก (`vehicleRequest.approve|reject`) และการเปลี่ยนระดับผู้อนุมัติ/สิทธิ์ผู้ใช้ (`user.update` พร้อมค่าก่อนแก้)

## 6. หน้าจอทั้งหมด (Screens)

### ผู้ใช้ทั่วไป (Employee)
1. หน้า Login (AD / Local)
2. หน้าแรก/แดชบอร์ด - สรุปการจองของฉัน (ห้อง+รถ)
3. หน้าปฏิทิน/ค้นหาห้องว่าง
4. หน้าจองห้องประชุม (สร้าง/แก้ไข/ยกเลิก, ตั้งจองซ้ำรายสัปดาห์)
5. หน้ารายการ/รายละเอียดการจองห้องของฉัน (รวมปุ่ม **เช็คอิน** สำหรับการจองที่ถึงเวลา)
6. หน้าฟอร์มส่งคำขอใช้รถ - แยกแท็บ **ขอรถนอก** / **ขอรถโอที** ในเมนู "จองรถ"
7. หน้ารายการคำขอรถของฉัน + สถานะ (แถวกระชับ, หน้าละ 7 รายการ เรียงคำขอล่าสุดก่อน - แสดง รออนุมัติ/ไม่อนุมัติ + ผู้อนุมัติ + เหตุผล)
8. หน้าโปรไฟล์ผู้ใช้ (ผู้อนุมัติ: อัปโหลด/เปลี่ยน/ลบลายเซ็น)
- หน้ารออนุมัติ (เฉพาะผู้มีระดับอนุมัติ - แท็บในเมนูจองรถ): รายการรอพิจารณา/ทั้งหมด, อนุมัติ, ไม่อนุมัติพร้อมเหตุผล
- ตัวสลับภาษา (ไทย/อังกฤษ) แสดงอยู่ทุกหน้า (ใน layout header)

### ผู้ดูแลระบบ (Admin)
> ตำแหน่งเมนูจริง (2026-09-30): **จองห้องประชุม** = จองห้องประชุม | รายการจองของฉัน | จัดการการจองห้อง\* - **จองรถ** = ขอรถนอก | ขอรถโอที | คำขอของฉัน | รออนุมัติ (ผู้อนุมัติ) | จัดการคำขอรถ\* | ตารางงานคนขับ\* | สายรถรับส่ง\* | ผู้โดยสารรถรับส่ง\* - **จัดการระบบ**\* = ห้องประชุม | คนขับและรถ (คนขับ / รถ / ผู้ให้บริการรถ) | อุปกรณ์ | แผนก | ผู้ใช้ (\* = Admin เท่านั้น)

9. หน้าจัดการห้องประชุม (เพิ่ม/แก้, ปิด-เปิดใช้งาน, ลบเฉพาะห้องที่ไม่เคยมีการจอง)
9a. หน้าจัดการการจองห้อง (เมนูจองห้องประชุม, Admin) - การจองของทุกคน: วันเวลา, ห้อง, หัวข้อ (+ รายสัปดาห์), ผู้จอง (ชื่อ/แผนก/เบอร์), สถานะ (+ เวลาเช็คอิน), จองเมื่อ (+ เวลายกเลิก); กรองช่วงวันที่ (วันนี้/7 วัน/30 วัน/ย้อนหลัง 30 วัน/กำหนดเอง), ห้อง, สถานะ (พร้อมจำนวน), ค้นหา; ยกเลิกการจองที่ยังไม่จบได้ (dev 2026-09-30)
10. หน้าจัดการคำขอรถ - ตัวกรองประเภทคำขอ/สถานะ, modal รายละเอียด (รวมเหตุผล/ผลการอนุมัติ), จัดรถ/คนขับ (รถนอกต้องอนุมัติก่อน), **ส่งออกแบบฟอร์ม W-HR-009 (PDF)**, รถโอทีดูแบบ **รวมตามสาย** (รายการเที่ยวรายวัน → ใบรายชื่อขึ้นรถ → จัดรถทั้งเที่ยว)
11. หน้าคนขับและรถ (คนขับ / รถ / ผู้ให้บริการรถ - ปิดใช้งาน หรือลบเฉพาะที่ไม่มีประวัติ) + ตารางงานคนขับรายสัปดาห์ (อยู่ในเมนูจองรถ)
12. หน้าจัดการผู้ใช้ (local account, นำเข้าจาก AD, กำหนด role, ระดับผู้อนุมัติ, แผนก, เบอร์โทร) + หน้าจัดการแผนก (โครงสร้างแผนกหลัก/แผนกย่อย)
13. หน้าจัดการอุปกรณ์ (จอ tablet: เพิ่ม/แก้/ลบ/ผูกห้อง/คัดลอกลิงก์/ออกลิงก์ใหม่/สถานะออนไลน์)
13a. หน้าสายรถรับส่ง (สาย, จุดจอด, เวลาวิ่ง, รถ+คนขับประจำ) และหน้าผู้โดยสารรถรับส่ง (สาย+จุดขึ้นรถของพนักงาน, ค้นหา/กรองสาย, หน้าละ 10 คน)
14. หน้ารายงาน (จัดการระบบ > รายงาน) 4 รายงาน: การใช้ห้องประชุม (ต่อห้อง/แผนก: จำนวน, ชั่วโมง, เช็คอิน, ปล่อยห้อง, ยกเลิก, อัตราเช็คอิน), คำขอรถ (ตามประเภท/สถานะ, แผนก, รายการทั้งหมด), การใช้รถและคนขับ (ตามแบบการจัดรถ/คนขับ/รถ: เที่ยว ชั่วโมง), รถโอทีตามสาย (ต่อสาย/รายวัน) - เลือกช่วงวันที่ + ส่งออก Excel (dev 2026-10-05)
15. หน้าบันทึกการใช้งาน (audit log) - จัดการระบบ > บันทึกการใช้งาน (`/admin/audit`, Admin เท่านั้น): ตัวกรองช่วงวันที่ (ตามเวลาไทย) / การกระทำ / ค้นหาผู้ใช้หรือรายละเอียด, แบ่งหน้า 50 รายการ, กดขยายดูค่าก่อนแก้และข้อมูลที่ส่งมา; ข้อความรหัส action แปลทั้ง 2 ภาษา (`audit.actions.*`)

### จอแสดงผลหน้าห้อง (Tablet - เข้าด้วย token ไม่ต้อง login)

## 7. Non-functional Requirements

- **2 ภาษา**: ไทย/อังกฤษ ผ่าน vue-i18n, สลับได้ทุกหน้า, จำภาษาไว้ (localStorage), ห้าม hardcode ข้อความรวม error message - **ทุกข้อความที่ผู้ใช้เห็นต้องเป็น key ใน `locales/th.json` และ `en.json` พร้อมกัน** (ทั้งป้าย, placeholder, title/aria-label, toast, confirm, ข้อความว่าง, alt, ชื่อแท็บเบราว์เซอร์) และเรียกผ่าน `t()`; รหัส error ใหม่ของ backend ต้องเพิ่มคำแปลใน `errors.*` ทั้ง 2 ภาษา; วันที่ใช้ `utils/datetime.js` (ปี ค.ศ. DD/MM/YYYY) ห้ามใช้ `toLocaleString('th-TH')`; ข้อยกเว้นที่อนุญาต (เอกสารฟอร์มทางการภาษาไทยตายตัวสำหรับพิมพ์, ค่าข้อมูลที่เก็บใน DB, ชื่อภาษาบนปุ่มสลับภาษา) ขึ้นทะเบียนพร้อมเหตุผลใน `frontend/scripts/check-i18n.mjs` (`ALLOW_THAI`); ตรวจอัตโนมัติด้วย `npm run lint:i18n` (ต้องผ่านก่อน commit)
- **Responsive / Mobile-first**: ทดสอบที่ 375px, 768px, **1024px (จอ laptop ที่เล็กที่สุดที่ต้องรองรับ - dev 2026-10-08: ห้ามหน้าเลื่อนแนวนอน, header/เมนูย่อยบรรทัดเดียว)**, 1440px, 1920px; **ความสูง notebook ที่เล็กที่สุด 560px** (หน้าเลื่อนแนวตั้งได้, header sticky, modal เลื่อนภายใน) - รายละเอียดใน UI-STYLE.md
- **Intranet-only / Offline-tolerant**: ทำงานได้แม้ไม่มีอินเทอร์เน็ต - ไม่มีส่วนไหนต้องใช้อินเทอร์เน็ตขาออกแล้ว (ตัด LINE ออก)
- **UI Style (บังคับ - dev อนุมัติ 2026-10-08)**: ทุกหน้าจอ **ทั้งหน้าใหม่ ฟีเจอร์ใหม่ และการแก้ไขหน้าเดิม** ต้องได้ style เดียวกันทั้งระบบตาม [`docs/UI-STYLE.md`](UI-STYLE.md) - โทนขาวสด/ดำคม + สีเน้น 1 สี (ดำ `#050505`), ขอบน้อย, ตารางแบนไม่มีกรอบ/เงา, มุมโค้ง 2 ระดับ, เมนูย่อยผ่าน `SubNav` เท่านั้น; ต้องใช้ token และ component class ที่ประกาศใน `frontend/src/style.css` (`btn`, `input`, `label`, `data-table`, `modal-*`, `chip` ฯลฯ) ห้ามเขียนสไตล์ปุ่ม/ช่องกรอก/modal เองในไฟล์ `.vue`; ต้นแบบอ้างอิง = หน้าจัดการแผนก; ตรวจอัตโนมัติด้วย `npm run lint:ui` (ต้องผ่านก่อน commit) - การเปลี่ยนหน้าตาระบบทั้งหมดให้แก้ที่ token ใน `style.css` ที่เดียว
- **Theme**: Business minimal (~~ใช้ skill UI UX Pro Max~~ - skill ไม่มีจริงใน environment, dev อนุมัติให้ออกแบบเองด้วย Tailwind), ฟอนต์ไทยสวยงามผ่าน @fontsource - จอ tablet ใช้ธีมสว่างเรียบแบบจอรถ Tesla
- **ไอคอน (บังคับ)** (dev 2026-10-07): ไอคอนทั้งระบบต้องเป็นสไตล์เดียวกับธีมเว็บ - SVG แบบเส้น (outline) 24×24, `stroke-width` 2, ใช้ `currentColor` (สีตามข้อความ/สถานะ ตาม token ใน UI-STYLE.md), ขนาด `h-4 w-4` (เล็ก `h-3.5`, ไอคอนปิด `h-5`) - **ห้ามใช้อีโมจิหรือตัวอักษรสัญลักษณ์เป็นไอคอน** (📍 ✕ ➕ ✓ ← → ฯลฯ) ทั้งเว็บรวมจอ tablet และ toast (ข้อยกเว้น: ลูกศร `→` ในประโยค/tooltip/ข้อความแปลที่เป็นแค่เครื่องหมายคั่นข้อความ เช่น "จัดการระบบ → คนขับ") ใช้ component กลาง `components/common/AppIcon.vue` และเพิ่มไอคอนใหม่ในไฟล์นั้นเท่านั้น (ไม่วาง SVG กระจายตามหน้า)
- **ปุ่มส่งออกข้อมูล (Export CSV/Excel/PDF) เห็นและใช้ได้เฉพาะ Admin** (dev 2026-10-07) - ซ่อนปุ่มด้วย `auth.isAdmin` และต้องไม่มีทางเรียกส่งออกจากฝั่งผู้ใช้อื่น (ฟังก์ชัน/API ส่งออกตรวจสิทธิ์ซ้ำ); ข้อมูลที่ผู้ใช้ทั่วไปเห็นบนหน้าจออยู่แล้ว ยังดูได้ตามปกติ แต่ไม่มีปุ่มดาวน์โหลด
- **ไม่ใช้ CDN ภายนอก**: ฟอนต์/ไอคอน/รูปภาพ self-host/bundle ทั้งหมด, ตรวจ dist ต้องไม่มี external URL หลงเหลือ, ใส่ CSP `'self'`
- **ขนาดผู้ใช้**: ประมาณ 50–200 คน, ใช้งานผ่าน Chrome/Edge เป็นหลัก
- **เขตเวลา/รูปแบบวันที่**: Asia/Bangkok (UTC+7) ทั้งระบบ, ปีค.ศ. (Gregorian) ทั้ง 2 ภาษา, รูปแบบวันที่ DD/MM/YYYY, เวลา 24 ชั่วโมง
- **ภาษาที่ใช้เขียนโค้ด**: **JavaScript ธรรมดา** ทั้ง frontend และ backend (dev ขอเปลี่ยนจาก TypeScript เนื่องจากไม่เคยใช้ TypeScript มาก่อน)
- **ฐานข้อมูล**: MSSQL Express ผ่าน `mssql` (tedious), SQL Authentication, instance `SQLEXPRESS`, collation `Thai_CI_AS`, มี migration + seed, parameterized query เท่านั้น, คำนึงถึงขีดจำกัด 10GB ต่อ database
- **Deploy**: Windows Server - IIS เสิร์ฟ frontend (static build), Node.js backend รันผ่าน PM2; รายละเอียด reverse proxy (IIS ARR + URL Rewrite เพื่อรวม origin) จะสรุปใน Phase 3 (ARCHITECTURE.md); ใช้ HTTP ภายใน intranet ก่อน (ยังไม่ทำ HTTPS ในเวอร์ชันแรก - เพิ่มทีหลังได้)
- **AD**: LDAP (plain, port 389); รายละเอียด domain/OU กำหนดผ่าน environment config ตอน deploy จริง (ต้องประสาน IT) - **ไม่มี admin group ใน AD** ผู้ใช้ที่ login ผ่าน AD ทุกคนเริ่มต้นเป็น Employee เสมอ Admin เป็นผู้กำหนด role ให้เองทีหลังผ่านหน้าจัดการผู้ใช้ในเว็บ
- **แจ้งเตือน**: **Email อย่างเดียว** ใช้แม่แบบเดียวกันทุกฉบับ - **อีเมลห้องประชุมเป็นภาษาอังกฤษ, อีเมลจองรถเป็นภาษาไทย** (dev 2026-09-30) - ผู้ส่ง booking@example.com; ผู้รับ: ผู้จอง/ผู้ขอ ตามเหตุการณ์ และ **คำขอรถใหม่ส่งถึงผู้ใช้ Admin ทุกคน** (ที่เปิดใช้งานและมีอีเมล) - ผ่าน SMTP ภายใน (ต้องขอรายละเอียด SMTP จาก IT ก่อน deploy จริง) - ~~LINE notification~~ ตัดออก (dev 2026-09-30)
- **Monitoring**: `GET /health` เช็คสถานะ API + การเชื่อมต่อ DB
- **Super Admin คนแรก**: dev จะสร้าง record ใน DB เอง - README ต้องมีตัวอย่าง SQL/ขั้นตอนไว้ให้อ้างอิง
- **Backup**: ถือเป็นหน้าที่ของ IT ผ่าน SQL Server maintenance plan ตามปกติ ระบบไม่ต้องมีฟีเจอร์ backup พิเศษ *(สมมติฐาน - โปรดยืนยันตอนรีวิว)*

## 8. สิ่งที่อยู่นอกขอบเขต (Out of Scope) - เวอร์ชันแรก

- Native mobile app (iOS/Android) - มีแค่ responsive web
- ระบบคำนวณค่าน้ำมัน/งบประมาณค่าใช้จ่ายรถ
- รองรับหลายบริษัท/multi-tenant

- การเชื่อมต่อ Outlook/Google Calendar หรือเครื่องมือภายนอกอื่น
- กรณีพนักงานเบิกรถขับเอง (self-drive)
- การสร้างเอกสาร PDF แบบฟอร์มขอรถสำหรับพิมพ์/เซ็นกระดาษ (เก็บข้อมูลในระบบพอสำหรับเวอร์ชันแรก)
- HTTPS (จะเพิ่มในเฟสถัดไปเมื่อพร้อม cert จาก internal CA)
